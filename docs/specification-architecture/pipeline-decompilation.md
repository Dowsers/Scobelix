# Traçabilité d'architecture — Pipeline de décompilation : désassemblage, exécution symbolique, structuration et simplification

Ce document trace chaque exigence de [../specification-fonctionnelle/pipeline-decompilation.md](../specification-fonctionnelle/pipeline-decompilation.md) vers son implémentation dans le code du dépôt Scobelix : fichier, fonction, et explication concise du mécanisme effectif. Les sections suivent l'ordre du document source ; les chemins sont relatifs à la racine du dépôt. Quand une exigence ne correspond à aucun code précis, cela est dit explicitement. « Vérifié en bac à sable » signale un comportement constaté en exécutant le décompilateur sur un bytecode d'essai ou sur un bytecode de `tests/fixtures/bytecode/`.

## 1. Vue d'ensemble

Le diagramme du document source correspond à l'enchaînement codé dans `scobelix/decompiler.py` (`_decompile_with_loader()`) : `Loader.load_binary()` puis `Loader.run()` (`scobelix/loader.py`, qui délègue l'analyse du dispatcher à `scobelix/dispatcher.py`), puis, pour chaque fonction, `VM.run()` (`scobelix/vm.py`) et `make_whiles()` (`scobelix/whiles.py`, qui délègue à `scobelix/simplify.py`), enfin `Function` (`scobelix/function.py`) et `Contract.postprocess()` (`scobelix/contract.py`), qui appelle `scobelix/folder.py` pour la vue texte.

## 6. Sémantique symbolique des opcodes

### 6.1 Arithmétique, comparaisons et bits

| Exigence | Fichier — Fonction/élément | Explication |
