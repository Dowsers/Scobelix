# Documentation fonctionnelle de Scobelix

## 1. Objet de ce répertoire

Scobelix est un décompilateur EVM générique, dérivé (fork) du décompilateur Panoramix : à partir du bytecode runtime d'un contrat, fourni directement ou récupéré auprès d'un nœud Ethereum à partir de son adresse, il produit un pseudo-code lisible, un AST JSON structuré (fonctions, traces, structure du stockage, slots de proxy reconnus, métadonnées du compilateur, analyse du dispatch) et, sur demande, une reconstruction Solidity qui conserve la sémantique EVM exacte de chaque fonction, aux limites signalées près. Cette reconstruction peut être validée par un compilateur Solidity externe et vérifiée contre le bytecode d'origine par exécution différentielle. Scobelix est livré comme bibliothèque Python importable et comme commande `scobelix`, sans aucun service réseau propre.

Ce répertoire `docs/` contient sa documentation fonctionnelle et architecturale, organisée en trois répertoires selon la nature de leur contenu :

- **[specification-fonctionnelle/](specification-fonctionnelle/)** — le comportement attendu du système, observable de l'extérieur (entrées acceptées, sorties produites, règles de décompilation, de génération et de vérification, contraintes), sous forme d'**exigences fonctionnelles** numérotées `FR-<PRÉFIXE>-NN`. Volontairement « boîte noire » : aucune référence au code.
- **[specification-parametrage/](specification-parametrage/)** — le format que doivent respecter les données de signatures, externes au code (fichier de signatures locales, fichier de signatures organisées, dump compressé, fichiers ABI d'entrée de l'outil de régénération, fichier de la base de signatures), pour être exploitables par Scobelix. Également « boîte noire ».
- **[specification-architecture/](specification-architecture/)** — la **traçabilité** de chaque exigence des deux répertoires précédents vers son implémentation réelle (fichier, fonction, explication). C'est le seul des trois répertoires qui cite du code.

Chaque exigence fonctionnelle est un item numéroté, assorti d'un énoncé « le système DOIT … » (obligatoire), « DEVRAIT … » (recommandation non bloquante), « PEUT … » (option) ou « NE DOIT PAS … » (interdiction). Huit préfixes sont utilisés, un par fichier thématique : `ARCH`, `DEC`, `STOR`, `SIG`, `SOL`, `SOR`, `INT`, `PARAM` (voir le sommaire ci-dessous). Ces exigences couvrent la nature du système et ses deux façades d'invocation, le pipeline de décompilation de bout en bout, la reconstruction des fonctions et du stockage, la résolution des signatures de fonctions, d'événements et d'erreurs, la reconstruction Solidity avec sa validation et sa vérification, le format exact des sorties, et les échanges du système avec son environnement.

Cette documentation est complémentaire du [README.md](../README.md) situé à la racine du dépôt, pas un remplacement : le README racine reste le document **opérationnel** — installation (y compris l'option `verify` et les compilateurs Solidity), exemples de commandes, emplacement de la base de signatures, procédure de test. Les fichiers de `specification-fonctionnelle/` et `specification-parametrage/` ne couvrent pas ce terrain ; ils décrivent exclusivement le comportement attendu et les contrats d'interface, sans jamais citer un fichier source, une fonction ou une ligne de code — un lecteur qui n'a jamais vu le code doit pouvoir les lire de bout en bout. `specification-architecture/` fait délibérément exception à cette règle : c'est son rôle.

## 2. Portée : ce que cette documentation ne couvre pas

- **Pas de catalogue de signatures.** Les entrées réelles de la table interne, du fichier de signatures organisées, du dump et du fichier de signatures locales sont des données : seul leur format est spécifié ([parametrage-signatures.md](specification-parametrage/parametrage-signatures.md)), et leur usage dans [resolution-signatures.md](specification-fonctionnelle/resolution-signatures.md).
- **Pas de preuve d'équivalence.** Le pseudo-code et la clé `trace` de l'AST restent une interprétation : des heuristiques de lisibilité non signalées s'y appliquent ([pipeline-decompilation.md](specification-fonctionnelle/pipeline-decompilation.md), section 9.1). La reconstruction Solidity est exacte par construction aux limites signalées près (indicateurs, notes et avertissements de chaque fonction), et sa vérification observe le comportement sur les appels essayés sans le prouver ([generation-solidity.md](specification-fonctionnelle/generation-solidity.md), section 7). La documentation décrit ces limites, leurs marqueurs et le sens de chaque verdict, jamais une garantie au-delà.
- **Pas l'intérieur des dépendances tierces.** La bibliothèque d'accès Ethereum, le compilateur Solidity et les machines EVM de la vérification ne sont décrits que par ce que le système en attend ([integration.md](specification-fonctionnelle/integration.md)).
- **Pas l'outil amont.** Seuls les comportements présents dans ce dépôt sont spécifiés, y compris les résidus hérités visibles (en-tête de la sortie texte, préfixe `PANORAMIX_` des variables d'environnement de budget).
- **Pas d'installation ni de mode d'emploi.** Installation, exemples de commandes et exécution des tests relèvent du README racine.
- **Pas la qualité du code.** Les constats de style hérités, le code mort et les auto-vérifications au chargement ne sont signalés, en notes contextuelles, que lorsqu'ils ont un effet observable.
- **Pas de publication ni de plateforme non supportée.** La publication sur un index public de paquets n'est pas vérifiable dans le dépôt ; Windows n'est pas supporté (le budget par fonction repose sur un signal d'horloge).
- **Pas d'intégration avec un programme appelant particulier.** Scobelix est un outil autonome : tout programme l'utilise par sa commande ou son interface Python, et le payload JSON combiné est son contrat d'intégration générique ([sorties.md](specification-fonctionnelle/sorties.md), section 4).

## 4. Glossaire rapide

- **Bytecode runtime** — le code EVM effectivement déployé d'un contrat, par opposition au bytecode de création ; seule forme d'entrée acceptée, en hexadécimal avec préfixe `0x` facultatif ; une entrée qui n'est pas un hexadécimal valide est refusée, la commande se terminant alors avec le code 2. Voir [architecture.md](specification-fonctionnelle/architecture.md), section 7, et [pipeline-decompilation.md](specification-fonctionnelle/pipeline-decompilation.md), section 2.
- **Métadonnées du compilateur** — l'objet CBOR que le compilateur place à la fin du bytecode (compilateur et version, notamment) ; reconnu, il est lu comme une donnée et non désassemblé, et exposé sous la clé `metadata` de l'AST. Voir [pipeline-decompilation.md](specification-fonctionnelle/pipeline-decompilation.md), section 2, et [sorties.md](specification-fonctionnelle/sorties.md), section 3.
- **Sélecteur (4 octets)** — les 4 premiers octets du keccak-256 de la signature canonique d'une fonction ou d'une erreur, `nom(type1,type2)`, normalisés en `0x` suivi de 8 chiffres hexadécimaux minuscules ; un événement est identifié par son topic0 complet de 32 octets. Voir [resolution-signatures.md](specification-fonctionnelle/resolution-signatures.md) et [parametrage-signatures.md](specification-parametrage/parametrage-signatures.md).
- **Dispatcher et points d'entrée** — le dispatcher est le code d'entrée qui compare le sélecteur d'appel à des constantes ; son analyse découpe le contrat en une fonction par sélecteur, plus une fonction de repli `_fallback(?)` et une fonction de réception `_receive(?)` lorsqu'elles existent ; un dispatcher non reconnu donne une fonction de repli unique couvrant tout le code. Le résumé de l'analyse est exposé sous la clé `dispatcher` de l'AST. Voir [pipeline-decompilation.md](specification-fonctionnelle/pipeline-decompilation.md), section 3.
- **Base de signatures** — fichier SQLite en lecture seule qui réunit quatre sources locales (table interne, fichier de signatures organisées, dump compressé, fichier de signatures locales), dont chaque entrée est vérifiée par son haché keccak-256, réparties en trois espaces de noms (fonctions, événements, erreurs) ; une recherche rend des candidats classés et la décompilation est entièrement hors ligne. Voir [resolution-signatures.md](specification-fonctionnelle/resolution-signatures.md), sections 2 et 3.
- **Fichier de la base de signatures** — `sigdb-<schéma>-<empreinte>.sqlite`, dans le répertoire de cache utilisateur (`~/.cache/scobelix` sous Linux), construit une seule fois lors de la première recherche (de l'ordre de 25 à 100 secondes), sous verrou et par renommage atomique ; toute modification des données désigne un nouveau fichier ; `SCOBELIX_SIGDB` en désigne un autre ; à défaut de répertoire de cache utilisable, un répertoire temporaire privé sert de repli ; une base indisponible laisse la décompilation se poursuivre sans noms. Voir [resolution-signatures.md](specification-fonctionnelle/resolution-signatures.md), section 3, et [integration.md](specification-fonctionnelle/integration.md), section 3.
- **Exécution symbolique** — interprétation du bytecode où les valeurs inconnues restent des expressions ; les chemins sont explorés en largeur jusqu'à épuisement ou jusqu'à un budget de nœuds ou de temps. Voir [pipeline-decompilation.md](specification-fonctionnelle/pipeline-decompilation.md), section 4.
- **Nœud d'exploration** — état de l'exécution symbolique identifié par la position, la hauteur de pile et les destinations de saut présentes dans la pile ; leur nombre est borné par `PANORAMIX_MAX_NODE_COUNT`. Voir [pipeline-decompilation.md](specification-fonctionnelle/pipeline-decompilation.md), section 4.
- **Élagage « protocol-safe »** — mécanisme toujours actif qui, au-delà de 60 % du budget de nœuds, remplace la branche fausse de tout nouveau saut indécidable par un nœud `undefined` portant `branch pruned`, sans l'explorer. Voir [pipeline-decompilation.md](specification-fonctionnelle/pipeline-decompilation.md), section 4.
- **Nœud `undefined`** — marqueur explicite d'une partie du code que le moteur n'a pas modélisée (branche élaguée, saut calculé à l'exécution, pile vide, terminaison de métadonnées atteinte, opcode non traité) ; le générateur Solidity l'écrit comme un rejet `scobelix: unsupported construct` et marque la fonction `unstructured`. Voir [pipeline-decompilation.md](specification-fonctionnelle/pipeline-decompilation.md), section 4, et [generation-solidity.md](specification-fonctionnelle/generation-solidity.md), section 1.
- **Trace exacte et trace d'affichage** — les deux formes de la trace structurée et simplifiée de chaque fonction, issues de la même exécution symbolique : la trace exacte, dont toutes les réécritures préservent la sémantique EVM, lue par le générateur Solidity et exposée par la seule interface Python ; la trace d'affichage, qui y ajoute des heuristiques de lisibilité non signalées et alimente le texte et la clé `trace` de l'AST. Voir [pipeline-decompilation.md](specification-fonctionnelle/pipeline-decompilation.md), sections 1 et 9.
- **Trace (représentation intermédiaire)** — liste de nœuds en n-uplets (`if`, `while`, `require`, `setvar`, `setmem`, `store`, `mask_shl`, `call`, `log`, `return`, `undefined`…) produite par l'exécution symbolique, puis structurée et simplifiée. Voir [pipeline-decompilation.md](specification-fonctionnelle/pipeline-decompilation.md), section 11.
- **`mask_shl`** — nœud (taille, décalage, décalage de sortie, valeur), tout en bits, qui représente l'extraction et le repositionnement d'un champ de bits ; affiché comme conversion de type. Voir [pipeline-decompilation.md](specification-fonctionnelle/pipeline-decompilation.md), section 11, et le fichier `OPCODES.md` du dépôt.
- **Limite de temps de la simplification** — la simplification d'une fonction s'arrête à sa limite de temps, au plus tard à 75 % du budget par fonction après le début de sa décompilation ; la fonction reste exacte mais incomplètement simplifiée, et elle est marquée `time_limited`. Voir [pipeline-decompilation.md](specification-fonctionnelle/pipeline-decompilation.md), section 8, et [architecture.md](specification-fonctionnelle/architecture.md), section 4.
- **Définition de stockage** — quadruplet (`def`, nom, emplacement, type) décrivant une variable d'état reconstruite (mapping, tableau, champ masqué, structure). Voir [reconstruction-fonctions-stockage.md](specification-fonctionnelle/reconstruction-fonctions-stockage.md), section 4, et [sorties.md](specification-fonctionnelle/sorties.md), section 3.
- **Emplacements hachés** — reconnaissance des constantes proches du haché keccak-256 d'un emplacement inférieur à 4 096 (élément ou membre des données d'un tableau dynamique ou d'une chaîne) et des hachés d'une clé et d'un emplacement (accès de mapping), qui permet de reconstruire tableaux et mappings. Voir [reconstruction-fonctions-stockage.md](specification-fonctionnelle/reconstruction-fonctions-stockage.md), section 4.1.
- **Getter / constante** — fonction dont la trace se réduit à retourner une valeur de stockage (getter, qui nomme la variable d'état lue) ou une valeur sans accès au stockage ni aux données d'appel (constante). Voir [reconstruction-fonctions-stockage.md](specification-fonctionnelle/reconstruction-fonctions-stockage.md), section 2.
- **Échecs (`problems`)** — fonctions dont la décompilation a levé une exception ou dépassé le budget par fonction ; listées dans le texte et l'AST, et écrites dans le Solidity généré comme des fonctions qui rejettent, de confiance `none`. Voir [architecture.md](specification-fonctionnelle/architecture.md), section 3, et [generation-solidity.md](specification-fonctionnelle/generation-solidity.md), section 2.
- **Indices de proxy (`proxy_hints`)** — constantes du bytecode égales à l'un des quatre slots de proxy standardisés ; purement indicatifs. Voir [reconstruction-fonctions-stockage.md](specification-fonctionnelle/reconstruction-fonctions-stockage.md), section 5.
- **Générateur Solidity (solgen)** — récrit chaque point d'entrée en Solidity 0.8 pour que le contrat produit se comporte comme le bytecode d'origine (mêmes sélecteurs, mêmes données d'appel acceptées ou rejetées, mêmes effets) ; ce qui n'a pas d'équivalent Solidity démontré est écrit avec sa sémantique EVM exacte (blocs `unchecked`, assemblage en ligne, mémoire émulée). Voir [generation-solidity.md](specification-fonctionnelle/generation-solidity.md), sections 1 et 3.
- **Fonction routée** — fonction dont le sélecteur n'a pas de nom retenu : son code forme une fonction privée `_fn_<sélecteur>`, appelée par la fonction de repli après un test de `msg.sig`, de sorte que les mêmes données d'appel produisent le même comportement. Voir [generation-solidity.md](specification-fonctionnelle/generation-solidity.md), section 2.
- **Réécritures et niveaux de réécriture (`tier`)** — onze réécritures remplacent la forme exacte par des formes Solidity usuelles (décodage ABI, variables d'état, getters, rejets, arithmétique, appels, événements, boucles, nommage, affectations composées, modificateurs) ; chaque fonction est au niveau `exact` (aucune réécriture), `idiomatic` (récrite) ou `partial` (récrite sans certaines réécritures) ; le paramètre `idiom_level` (`exact` ou `full`) les désactive toutes ou les autorise. Voir [generation-solidity.md](specification-fonctionnelle/generation-solidity.md), sections 4 et 6.
- **Gardes statiques** — indicateurs de risque du code d'une fonction (échec du décompilateur, construction non traduite, limite signalée du moteur, relevé en mode dégradé…) qui la maintiennent au niveau exact. Voir [generation-solidity.md](specification-fonctionnelle/generation-solidity.md), section 6.
- **Confiance** — indicateur par fonction (`high`, `medium`, `low`, `none`) dérivé de son verdict et de ses indicateurs : `high` seulement pour une fonction vérifiée `EQUIVALENT` sans indicateur de risque ; `medium` pour une fonction non vérifiée, exacte ou récrite ; `low` pour une différence observée ou du code non traduit ; `none` pour un échec du décompilateur. Voir [generation-solidity.md](specification-fonctionnelle/generation-solidity.md), section 6.
- **Validation par compilation** — compilation facultative du Solidity généré par un compilateur installé ou, sur autorisation, téléchargé, avec repli sur le pipeline IR lorsque le pipeline par défaut manque d'emplacements de pile ; statut `valid`, `invalid` ou `skipped` ; atteste la compilabilité, jamais la fidélité. Voir [generation-solidity.md](specification-fonctionnelle/generation-solidity.md), section 5.
- **Niveaux de vérification L0 à L4** — L0 : le texte compile ; L1 : même interface externe (sélecteurs, mutabilité, événements, erreurs) ; L2 : chaque variable d'état déclarée est à l'emplacement inféré ; L3 : comportement équivalent observé par exécution différentielle contre l'original, sur les machines EVM de l'option `verify` ; L4 : bytecode compilé identique à l'original, métadonnées et immuables mis à part (un bonus, dont l'absence n'est pas un échec). Voir [generation-solidity.md](specification-fonctionnelle/generation-solidity.md), section 7, et [sorties.md](specification-fonctionnelle/sorties.md), section 6.
- **Verdicts** — résultat de la vérification pour chaque fonction : `EQUIVALENT`, `EQUIVALENT_REVERTS_ONLY` (aucune différence, mais l'original a rejeté tous les appels essayés), `DIVERGENT` (avec un contre-exemple), `MISSING`, `EXTRA`, `ROUTED`, `INCONCLUSIVE` (différence que l'environnement peut expliquer) et `SKIPPED` ; `unverified` sans vérification. Voir [sorties.md](specification-fonctionnelle/sorties.md), section 6.
- **Boucle de vérification** — avec vérification, le générateur garde pour chaque fonction la forme la plus idiomatique dont une exécution contre l'original a été acceptée, en retirant des réécritures (réparation de la compilation, exclusion de variables mal placées, recherche par exécution) et en écrivant les autres fonctions au niveau exact ; elle est bornée par un budget (300 secondes et 20 exécutions par défaut). Voir [generation-solidity.md](specification-fonctionnelle/generation-solidity.md), section 7.
- **Résolution des compilateurs** — recherche des versions de solc installées (répertoire `SCOBELIX_SOLC_DIR`, cache de l'application, répertoires des gestionnaires de versions usuels, `PATH`), choix d'une version que les pragmas acceptent, et téléchargement facultatif d'une version officielle contrôlée par empreinte SHA-256, seulement sur autorisation. Voir [integration.md](specification-fonctionnelle/integration.md), section 2.
- **Payload combiné** — objet JSON sur une seule ligne réunissant texte et AST et, sur demande, reconstruction Solidity avec confiance, avertissements et table des fonctions, rapport de vérification et statut de validation ; destiné à tout programme appelant. Voir [sorties.md](specification-fonctionnelle/sorties.md), section 4.
- **Budgets** — quatre délais configurables (par fonction, exécution symbolique, simplification, découverte des fonctions) et un nombre maximal de nœuds ; leur dépassement dégrade le résultat au lieu d'interrompre la décompilation. Voir [architecture.md](specification-fonctionnelle/architecture.md), section 4.

- **Productions à la demande** — le code Solidity généré (contrat `Decompiled` par défaut), le rapport de vérification, le fichier de profil `scobelix.prof` et le payload combiné ; formats dans [sorties.md](specification-fonctionnelle/sorties.md) et [generation-solidity.md](specification-fonctionnelle/generation-solidity.md).

## 6. Note de maintenance

Plusieurs chiffres cités dans cette documentation sont vivants et datés du 2026-10-15 : 2 034 tests collectés, dont 1 734 dans l'exécution par défaut ; 48 bytecodes et 30 sources de référence ; 121 sélecteurs dans la table interne, 1 004 entrées dans le fichier de signatures organisées, 557 dans le fichier de signatures locales et 1 534 891 lignes dans le dump (dont 391 340 substituts sans information, rejetés) ; environ 117 Mio pour le fichier de la base de signatures ; 4 slots de proxy ; version 0.7.4 du paquet. Ils ne doivent pas être recopiés tels quels ailleurs : la source de vérité de chacun (fichier de données, table du code, suite de tests, manifeste du projet) est indiquée dans les documents de traçabilité, où il peut être recompté.

Points de dérive connus entre l'usage attendu et le comportement réel, signalés en notes contextuelles ou spécifiés tels qu'ils sont : la nature de l'argument positionnel de la commande se décide sur sa longueur, une chaîne de 42 caractères étant prise pour une adresse à moins que `--bytecode` ne soit passé, le contenu de l'entrée standard étant toujours un bytecode ([architecture.md](specification-fonctionnelle/architecture.md), section 7) ; les options de la génération Solidity employées sans `--solidity` sont ignorées sans message (même section) ; l'en-tête hérité `# Palkeoramix decompiler. ` de la sortie texte ne porte pas le nom du système ([sorties.md](specification-fonctionnelle/sorties.md), section 2) ; les scripts de vérification hérités ont été remplacés par la suite de tests ([integration.md](specification-fonctionnelle/integration.md), section 7).
