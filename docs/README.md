# Documentation fonctionnelle de Scobelix

## 1. Objet de ce répertoire

Scobelix est un décompilateur EVM générique, dérivé (fork) du décompilateur Panoramix : à partir du bytecode runtime d'un contrat, fourni directement ou récupéré auprès d'un nœud Ethereum à partir de son adresse, il produit un pseudo-code lisible, un AST JSON structuré (fonctions, traces, structure du stockage, slots de proxy reconnus) et, sur demande, une reconstruction Solidity « best-effort » éventuellement validée par un compilateur externe. Il est livré comme bibliothèque Python importable et comme commande `scobelix`, sans aucun service réseau propre.

Ce répertoire `docs/` contient sa documentation fonctionnelle et architecturale, organisée en trois répertoires selon la nature de leur contenu :

- **[specification-fonctionnelle/](specification-fonctionnelle/)** — le comportement attendu du système, observable de l'extérieur (entrées acceptées, sorties produites, règles de décompilation, contraintes), sous forme d'**exigences fonctionnelles** numérotées `FR-<PRÉFIXE>-NN`. Volontairement « boîte noire » : aucune référence au code.
- **[specification-parametrage/](specification-parametrage/)** — le format que doivent respecter les données de signatures de 4 octets, externes au code (fichier de signatures locales, dump compressé, fichiers ABI d'entrée de l'outil de régénération), pour être exploitables par Scobelix. Également « boîte noire ».
- **[specification-architecture/](specification-architecture/)** — la **traçabilité** de chaque exigence des deux répertoires précédents vers son implémentation réelle (fichier, fonction, explication). C'est le seul des trois répertoires qui cite du code.

Chaque exigence fonctionnelle est un item numéroté, assorti d'un énoncé « le système DOIT … » (obligatoire), « DEVRAIT … » (recommandation non bloquante), « PEUT … » (option) ou « NE DOIT PAS … » (interdiction). Huit préfixes sont utilisés, un par fichier thématique : `ARCH`, `DEC`, `STOR`, `SIG`, `SOL`, `SOR`, `INT`, `PARAM` (voir le sommaire ci-dessous). Ces exigences couvrent la nature du système et ses deux façades d'invocation, le pipeline de décompilation de bout en bout, la reconstruction des fonctions et du stockage, la résolution des sélecteurs de fonctions, la reconstruction Solidity et sa validation, le format exact des sorties, et les échanges du système avec son environnement.

Cette documentation est complémentaire du [README.md](../README.md) situé à la racine du dépôt, pas un remplacement : le README racine reste le document **opérationnel** — installation, exemples de commandes, procédure de test. Les fichiers de `specification-fonctionnelle/` et `specification-parametrage/` ne couvrent pas ce terrain ; ils décrivent exclusivement le comportement attendu et les contrats d'interface, sans jamais citer un fichier source, une fonction ou une ligne de code — un lecteur qui n'a jamais vu le code doit pouvoir les lire de bout en bout. `specification-architecture/` fait délibérément exception à cette règle : c'est son rôle.

## 2. Portée : ce que cette documentation ne couvre pas

- **Pas de catalogue de signatures.** Les entrées réelles du dump de signatures, du fichier de signatures locales et de la table interne sont des données : seul leur format est spécifié ([parametrage-signatures.md](specification-parametrage/parametrage-signatures.md)), et leur usage dans [resolution-signatures.md](specification-fonctionnelle/resolution-signatures.md).
- **Pas de garantie de fidélité sémantique.** Le système est explicitement approximatif : la documentation décrit les approximations, leurs marqueurs et leurs limites connues, jamais une garantie que le pseudo-code ou le Solidity reconstruit se comporte comme le bytecode d'origine.
- **Pas l'intérieur des dépendances tierces.** La bibliothèque d'accès Ethereum, le compilateur Solidity et le sélecteur de versions de compilateur ne sont décrits que par ce que le système en attend ([integration.md](specification-fonctionnelle/integration.md)).
- **Pas l'outil amont.** Seuls les comportements présents dans ce dépôt sont spécifiés, y compris les résidus hérités visibles (en-tête de la sortie texte, préfixe `PANORAMIX_` des variables d'environnement).
- **Pas d'installation ni de mode d'emploi.** Installation, exemples de commandes et exécution des tests relèvent du README racine.
- **Pas la qualité du code.** Les constats de style hérités, le code mort et les auto-vérifications au chargement ne sont signalés, en notes contextuelles, que lorsqu'ils ont un effet observable.
- **Pas de publication ni de plateforme non supportée.** La publication sur un index public de paquets n'est pas vérifiable dans le dépôt ; Windows n'est pas supporté.
- **Pas d'intégration avec un programme appelant particulier.** Scobelix est un outil autonome : tout programme l'utilise par sa commande ou son interface Python, et le payload JSON combiné est son contrat d'intégration générique ([sorties.md](specification-fonctionnelle/sorties.md), section 4).

## 4. Glossaire rapide

- **Bytecode runtime** — le code EVM effectivement déployé d'un contrat, par opposition au bytecode de création ; seule forme d'entrée acceptée, en hexadécimal avec préfixe `0x` facultatif. Voir [architecture.md](specification-fonctionnelle/architecture.md).
- **Sélecteur (4 octets)** — les 4 premiers octets du keccak-256 de la signature canonique d'une fonction, `nom(type1,type2)`, normalisés en `0x` suivi de 8 chiffres hexadécimaux minuscules. Voir [resolution-signatures.md](specification-fonctionnelle/resolution-signatures.md) et [parametrage-signatures.md](specification-parametrage/parametrage-signatures.md).
- **Base de signatures** — les trois sources consultées dans un ordre strict pour nommer un sélecteur : table interne, cache disque construit depuis le dump embarqué, fichier de signatures locales ; entièrement hors ligne. Voir [resolution-signatures.md](specification-fonctionnelle/resolution-signatures.md).
- **Cache de signatures** — base clé-valeur sur disque, dans le répertoire de cache utilisateur, construite à la première résolution par décompression du dump et jamais invalidée automatiquement. Voir [resolution-signatures.md](specification-fonctionnelle/resolution-signatures.md), section 3, et [integration.md](specification-fonctionnelle/integration.md), section 3.
- **Exécution symbolique** — interprétation du bytecode où les valeurs inconnues restent des expressions ; les chemins sont explorés en largeur jusqu'à épuisement ou jusqu'à un budget de nœuds ou de temps. Voir [pipeline-decompilation.md](specification-fonctionnelle/pipeline-decompilation.md), section 4.
- **Nœud d'exploration** — état de l'exécution symbolique identifié par la position, la hauteur de pile et les destinations de saut présentes dans la pile ; leur nombre est borné par `PANORAMIX_MAX_NODE_COUNT`. Voir [pipeline-decompilation.md](specification-fonctionnelle/pipeline-decompilation.md), section 4.
- **Élagage « protocol-safe »** — mécanisme toujours actif qui, au-delà de 60 % du budget de nœuds, remplace la branche fausse de tout saut indécidable par un arrêt, au prix d'une trace incomplète non signalée. Voir [pipeline-decompilation.md](specification-fonctionnelle/pipeline-decompilation.md), section 4.
- **Trace (représentation intermédiaire)** — liste de nœuds en n-uplets (`if`, `while`, `require`, `setvar`, `setmem`, `store`, `mask_shl`, `call`, `log`, `return`…) produite par l'exécution symbolique, structurée et simplifiée, puis rendue en texte, sérialisée dans l'AST JSON et traduite en Solidity. Voir [pipeline-decompilation.md](specification-fonctionnelle/pipeline-decompilation.md), section 11.
- **`mask_shl`** — nœud (taille, décalage, décalage de sortie, valeur), tout en bits, qui représente l'extraction et le repositionnement d'un champ de bits ; affiché comme conversion de type. Voir [pipeline-decompilation.md](specification-fonctionnelle/pipeline-decompilation.md), section 11, et le fichier `OPCODES.md` du dépôt.
- **Fonction de repli (`_fallback`)** — l'unique point d'entrée reconstruit en pratique, qui contient l'arbre de dispatch par sélecteur de tout le contrat. Voir [pipeline-decompilation.md](specification-fonctionnelle/pipeline-decompilation.md), section 3.
- **Arbre de dispatch** — suite de comparaisons du sélecteur d'appel avec des constantes, que le système affiche sous forme de signatures lorsque la base de signatures les connaît. Voir [resolution-signatures.md](specification-fonctionnelle/resolution-signatures.md), section 4.2.
- **Définition de stockage** — quadruplet (`def`, nom, emplacement, type) décrivant une variable d'état reconstruite (mapping, tableau, champ masqué, structure). Voir [reconstruction-fonctions-stockage.md](specification-fonctionnelle/reconstruction-fonctions-stockage.md), section 4, et [sorties.md](specification-fonctionnelle/sorties.md), section 3.
- **Table arc-en-ciel des slots** — table précalculée des hachés keccak-256 des emplacements 0 à 19 et des clés 0 et 1 sur ces emplacements, utilisée pour reconnaître mappings et tableaux. Voir [reconstruction-fonctions-stockage.md](specification-fonctionnelle/reconstruction-fonctions-stockage.md), section 4.1.
- **Getter / constante** — fonction dont la trace se réduit à retourner une valeur de stockage (getter, qui nomme la variable d'état lue) ou une valeur sans accès au stockage ni aux données d'appel (constante). Voir [reconstruction-fonctions-stockage.md](specification-fonctionnelle/reconstruction-fonctions-stockage.md), section 2.
- **Échecs (`problems`)** — fonctions dont la décompilation a levé une exception ou dépassé le budget par fonction ; listées dans le texte, l'AST et, en commentaire, dans le Solidity généré. Voir [architecture.md](specification-fonctionnelle/architecture.md), section 3.
- **Indices de proxy (`proxy_hints`)** — constantes du bytecode égales à l'un des quatre slots de proxy standardisés ; purement indicatifs. Voir [reconstruction-fonctions-stockage.md](specification-fonctionnelle/reconstruction-fonctions-stockage.md), section 5.
- **Solgen / confiance** — le générateur de reconstruction Solidity et son indicateur par fonction (`high`, `medium`, `low`), calculé sur la proportion de nœuds non résolus. Voir [generation-solidity.md](specification-fonctionnelle/generation-solidity.md).
- **Validation par compilation** — compilation facultative du Solidity généré par un compilateur externe ; statut `valid`, `invalid` ou `skipped` ; atteste la compilabilité, jamais la fidélité. Voir [generation-solidity.md](specification-fonctionnelle/generation-solidity.md), section 5.
- **Payload combiné** — objet JSON sur une seule ligne réunissant texte, AST et, sur demande, reconstruction Solidity et validation, destiné à tout programme appelant. Voir [sorties.md](specification-fonctionnelle/sorties.md), section 4.
- **Budgets** — quatre délais configurables (par fonction, exécution symbolique, simplification, découverte des fonctions) et un nombre maximal de nœuds ; leur dépassement dégrade le résultat au lieu d'interrompre la décompilation. Voir [architecture.md](specification-fonctionnelle/architecture.md), section 4.

## 6. Note de maintenance

Plusieurs chiffres cités dans cette documentation sont vivants et datés du 2026-09-29 : 52 tests, 8 bytecodes et 9 sources de référence, 557 entrées dans le fichier de signatures locales, 1 534 891 lignes dans le dump (dont environ un quart de noms synthétiques), 121 sélecteurs distincts dans la table interne, 11 événements connus, 4 slots de proxy, version 0.7.3 du paquet. Ils ne doivent pas être recopiés tels quels ailleurs : la source de vérité de chacun (fichier de données, table du code, suite de tests, manifeste du projet) est indiquée dans les documents de traçabilité, où il peut être recompté.

Points de dérive connus entre la documentation d'usage et le comportement réel, signalés en notes contextuelles plutôt que spécifiés : le README racine annonce un « stub » qui rejette l'exécution pour chaque fonction en échec, alors que le générateur n'émet que deux commentaires ([generation-solidity.md](specification-fonctionnelle/generation-solidity.md), section 4) ; la description héritée du pipeline et l'option `--function` supposent une découverte des fonctions par sélecteur qui n'a plus lieu ([pipeline-decompilation.md](specification-fonctionnelle/pipeline-decompilation.md), section 3) ; les scripts de vérification hérités ont été remplacés par la suite de tests ([integration.md](specification-fonctionnelle/integration.md), section 7).
