# Intégration de Scobelix dans son environnement

Ce document (préfixe `INT`) spécifie tout ce que le système échange avec l'extérieur et ce qu'il attend de ces tiers : le nœud Ethereum interrogé en mode adresse, le compilateur Solidity invoqué comme binaire externe (localisation et téléchargement compris), les machines EVM de la vérification, le système de fichiers (base de signatures, données embarquées, compilateurs téléchargés, fichier de profil), la distribution sous forme de paquet installable, l'intégration continue et le versionnage automatique, la suite de tests considérée comme contrat de non-régression, et le statut des scripts de vérification hérités. Scobelix étant un outil autonome, il n'a pas d'autre intégration : tout programme appelant l'utilise par sa commande ou par son interface Python, décrites dans [architecture.md](architecture.md), sections 7 et 8, et peut s'appuyer sur le payload combiné de [sorties.md](sorties.md), section 4.

Ce document ne redécrit ni la sémantique de la validation et de la vérification par génération ([generation-solidity.md](generation-solidity.md)), ni celle du rapport de vérification ([sorties.md](sorties.md), section 6), ni celle de la base de signatures ([resolution-signatures.md](resolution-signatures.md), section 3) : il en fixe le contrat externe. Voir [README.md](../README.md) pour la table des matières du répertoire `docs/`.

Chaque exigence est identifiée par un code FR-INT-NN. Sauf mention contraire (« DEVRAIT », « PEUT », « NE DOIT PAS »), une exigence est obligatoire (« DOIT »).

## 1. Nœud Ethereum (mode adresse)

- **FR-INT-01** : La lecture du code d'un contrat auprès d'un nœud Ethereum, seul échange réseau du système en dehors du téléchargement autorisé d'un compilateur (voir [architecture.md](architecture.md), section 1), DOIT n'être déclenchée que par une décompilation depuis une adresse (argument de 42 caractères de la commande sans l'option `--bytecode` — jamais le contenu de l'entrée standard —, ou fonction de décompilation par adresse de l'interface Python).
- **FR-INT-02** : Le système DOIT exiger une adresse composée uniquement de caractères alphanumériques (une adresse contenant tout autre caractère provoque une erreur avant tout accès réseau), la convertir en minuscules, puis au format checksum avant l'interrogation ; une adresse alphanumérique qui n'est pas une adresse hexadécimale valide est rejetée par cette conversion, également avant tout accès réseau.

*Note contextuelle : le contrôle du caractère alphanumérique est une auto-vérification interne, qui disparaît lorsque l'interpréteur est lancé en mode optimisé ; l'adresse invalide est alors rejetée par la seule conversion au format checksum.*
- **FR-INT-03** : Le système DOIT demander le code déployé à l'adresse pour le bloc le plus récent, puis décompiler le code hexadécimal obtenu exactement comme un bytecode fourni directement ; un compte sans code DOIT aboutir au résultat « aucun code » de [architecture.md](architecture.md), section 2.
- **FR-INT-04** : Le nœud interrogé DOIT être déterminé par la bibliothèque d'accès Ethereum, qui retient le premier point d'accès joignable dans l'ordre suivant : celui que désigne `WEB3_PROVIDER_URI` (schéma `http`/`https`, `ws`/`wss` ou `file` pour une socket IPC) lorsqu'elle est définie, puis les points d'accès locaux par défaut (socket IPC, HTTP puis WebSocket) ; un point désigné mais injoignable est donc silencieusement remplacé par un nœud local joignable, un schéma non pris en charge provoque une erreur, et en l'absence de tout nœud joignable l'erreur de la bibliothèque DOIT être propagée.
- **FR-INT-05** : Le système NE DOIT appliquer ni reprise sur erreur ni délai d'attente propre à l'interrogation du nœud : toute erreur du nœud ou du transport DOIT être propagée à l'appelant sans être transformée.
- **FR-INT-06** : Le système DOIT attendre du tiers un point d'accès JSON-RPC Ethereum qui réponde à la lecture du code d'un compte (méthode standard de lecture du code) par le bytecode runtime en hexadécimal.

## 2. Compilateur Solidity et machines EVM (tiers facultatifs)

Ni le compilateur ni les machines EVM ne sont des dépendances obligatoires du paquet (voir [architecture.md](architecture.md), section 5) : le premier est un binaire externe que le système trouve ou télécharge, les secondes une option d'installation.

### 2.1 Compilateur Solidity

Le compilateur n'est pas une dépendance déclarée du paquet ; son usage par la génération, la validation et la vérification, son délai maximal et le traitement de son absence sont spécifiés dans [generation-solidity.md](generation-solidity.md), sections 5 et 7. Cette section fixe ce que le système attend de lui, comment il le trouve et comment il peut le télécharger.

- **FR-INT-07** : Le système DOIT attendre du compilateur : une version publiée identifiable par son option `--version`, dont la sortie contient `Version: X.Y.Z` sans suffixe de préversion (une préversion, `-nightly…`, n'est jamais retenue) ; l'option `--standard-json`, avec une entrée JSON sur son entrée standard et le résultat JSON sur sa sortie standard (génération et vérification) ; l'option `--bin` suivie d'un chemin de fichier et, à partir de la version 0.8.13, sa variante `--via-ir --optimize --bin` (validation), avec un code de sortie non nul en cas d'échec et des diagnostics sur sa sortie d'erreur dont les lignes commencent par `Error` ou `Warning`. Le code généré demande une version 0.8 au moins égale à 0.8.2 (`pragma solidity ^0.8.N;`, N ≥ 2) et, lorsque l'original l'emploie, l'ancien codeur ABI (`pragma abicoder v1;`).
- **FR-INT-08** : Le système DOIT rechercher les compilateurs installés dans cet ordre, le premier trouvé pour une version l'emportant : les fichiers `solc*` du répertoire `SCOBELIX_SOLC_DIR` ; le répertoire `solc` du répertoire de cache utilisateur de l'application `scobelix` (destination des téléchargements) ; `~/.solcx/solc-v*` ; `~/.solc-select/artifacts/solc-*/solc-*` ; `~/.svm/*/solc-*` ; les caches de compilateurs de hardhat (`~/.cache/hardhat-nodejs/compilers*/*/solc-*` et `~/Library/Caches/hardhat-nodejs/compilers*/*/solc-*`) ; enfin les fichiers `solc*` des répertoires du `PATH`. Chaque candidat exécutable DOIT être identifié en l'exécutant avec `--version`, jamais d'après son nom ; un script (fichier commençant par `#!`) NE DOIT PAS être retenu.

*Note contextuelle : l'exclusion des scripts vise l'aiguillage installé dans le `PATH` par le sélecteur de versions solc-select, qui honore `SOLC_VERSION` et termine avec le code 0 et une sortie vide lorsque la version demandée manque, ce qui ferait passer une compilation ratée pour réussie.*

- **FR-INT-09** : Lorsqu'une version est imposée (version visée par la génération, ou version demandée à la vérification), le système DOIT employer exactement cette version, installée ou, si le téléchargement est autorisé, téléchargée ; à défaut, il DOIT retenir la version préférée lorsque tous les pragmas du code l'acceptent et qu'elle est installée ou téléchargeable, sinon la plus récente version installée que les pragmas acceptent, sinon, téléchargement autorisé, la plus récente version officielle qu'ils acceptent ; faute de compilateur, l'étape concernée est déclarée impossible (validation `skipped`, niveau L0 de la vérification `skipped`) avec un message qui énumère les versions installées et indique comment autoriser le téléchargement.
- **FR-INT-10** : Le téléchargement d'un compilateur DOIT n'avoir lieu qu'avec l'autorisation de [architecture.md](architecture.md), FR-ARCH-30, et se limiter aux versions officielles publiées sur `https://binaries.soliditylang.org` pour la plateforme courante (`linux-amd64`, `macosx-amd64` ou `windows-amd64`) : le système DOIT lire la liste `list.json` de la plateforme, télécharger le binaire de la version, vérifier son empreinte SHA-256 contre celle de la liste puis la version qu'il annonce, et seulement alors l'installer, par un renommage atomique, sous le nom `solc-<version>` dans `SCOBELIX_SOLC_DIR` ou, à défaut, dans le répertoire `solc` du répertoire de cache utilisateur ; les requêtes DOIVENT porter un en-tête `User-Agent` propre au système, le serveur refusant celui de la bibliothèque standard.

### 2.2 Machines EVM de la vérification

- **FR-INT-11** : Le système DOIT exécuter le niveau L3 de la vérification sur deux machines EVM facultatives, installées par l'option `verify` du paquet (voir [architecture.md](architecture.md), section 5) : par défaut, pyrevm, rapide, exécute l'essentiel des appels et py-evm, instrumentable, confirme les différences, mesure la couverture et suit les comparaisons ; lorsqu'une seule est installée, elle exécute seule tous les appels ; une machine DOIT être considérée comme disponible seulement si son paquet s'importe sans erreur, et chacune exécute par défaut les règles de la version Cancun d'Ethereum.
- **FR-INT-12** : Sans machine EVM, ou sans compilateur, la génération avec vérification DOIT produire son code sans erreur : les fonctions sont écrites sous leur forme exacte et non vérifiées, la raison figure dans les avertissements et le résumé de vérification, et la commande se termine avec le code 0 ([architecture.md](architecture.md), section 7).

*Note contextuelle : les originaux qui emploient des opcodes postérieurs à Cancun (par exemple CLZ, produit par solc 0.8.31 pour la cible osaka) ne peuvent être exécutés ni par pyrevm 0.3.7 ni par py-evm 0.12.*

## 3. Système de fichiers

- **FR-INT-13** : Le système DOIT placer la base de signatures dans le répertoire de cache utilisateur standard de la plateforme pour l'application `scobelix` (sous Linux, `~/.cache/scobelix`, ou le sous-répertoire `scobelix` de `XDG_CACHE_HOME` lorsque cette variable est définie), créé à la demande, sous le nom `sigdb-<schéma>-<empreinte>.sqlite`, où l'empreinte (16 chiffres hexadécimaux) dépend des données de signatures embarquées : une nouvelle version des données ou du format sélectionne un nouveau fichier. La base DOIT être construite une seule fois, à la première utilisation, dans un fichier temporaire renommé ensuite atomiquement, sous un verrou exclusif `<nom>.lock` qui fait attendre les autres processus, puis ouverte en lecture seule (voir [resolution-signatures.md](resolution-signatures.md), section 3).
- **FR-INT-14** : Le système DOIT permettre de choisir un autre fichier pour la base par la variable `SCOBELIX_SIGDB` (fichier existant ou à construire) ; un fichier existant à cet emplacement qui n'est pas une base de signatures NE DOIT jamais être remplacé (la base est alors indisponible). Lorsque le répertoire de cache n'est pas utilisable, le système DOIT se replier sur un sous-répertoire privé de l'utilisateur dans le répertoire temporaire (`scobelix-<uid>`, droits 0700), et l'ignorer s'il n'est pas privé ; aucune option ne désactive la base. Son volume observé est d'environ 117 Mio.

*Note contextuelle : les fichiers d'anciennes versions de la base (ou de l'ancien cache de signatures) restés dans le répertoire de cache ne sont jamais supprimés ; seuls les fichiers temporaires vieux de plus d'une heure laissés par une construction interrompue le sont.*

- **FR-INT-15** : Le système DOIT lire ses fichiers de données de signatures (dump compressé, signatures locales et signatures organisées) à l'intérieur du paquet installé ; seul l'outil de régénération, avec sa destination par défaut, écrit dans le paquet, ce qui suppose un droit d'écriture sur l'installation.
- **FR-INT-16** : Le système NE DOIT écrire dans le répertoire courant que le fichier de profil `scobelix.prof`, et seulement sur demande (`--profile`).
- **FR-INT-17** : La validation par compilation DOIT n'utiliser qu'un répertoire temporaire propre à chaque invocation, supprimé à la fin de celle-ci, y compris en cas d'échec ou de dépassement de délai.
- **FR-INT-18** : En dehors du répertoire courant, le système NE DOIT écrire que la base de signatures, son verrou et ses fichiers temporaires (FR-INT-13, FR-INT-14), les compilateurs téléchargés (FR-INT-10) et le répertoire temporaire de la validation (FR-INT-17) ; la vérification compile en mémoire (entrée et sortie standard du compilateur) et n'écrit aucun fichier.

*Note contextuelle : les fichiers de données embarqués (environ 22,8 Mio pour le dump) sont suivis directement par le gestionnaire de versions du dépôt, sans mécanisme dédié aux fichiers volumineux.*

## 4. Distribution sous forme de paquet

- **FR-INT-19** : Le système DOIT être distribué comme un paquet Python construit par le moteur de construction poetry-core (version 1.2.0 ou ultérieure), dont la version unique est déclarée dans le manifeste du projet au format `X.Y.Z` (0.7.4 à la date de ce document).
- **FR-INT-20** : Le paquet DOIT déclarer le script console `scobelix`, la contrainte d'interpréteur `>=3.9,<4` (voir [architecture.md](architecture.md), section 5), les dépendances d'exécution (journalisation colorée ^15, client HTTP ^2, bibliothèque d'accès Ethereum 6.0.0-beta.8 avec autorisation des préversions, délais par signaux ^0.5, répertoires utilisateur ^1.4), l'option d'installation `verify` qui ajoute les machines EVM pyrevm 0.3.7 (sur les plateformes où elle est publiée précompilée) et py-evm 0.12.1b1, et, dans un groupe séparé de dépendances de développement, l'outil de test pytest ^7.
- **FR-INT-21** : Le paquet DOIT inclure les trois fichiers de données de signatures situés dans son arborescence, de sorte qu'une installation soit fonctionnelle sans téléchargement complémentaire.
- **FR-INT-22** : La configuration de test du paquet DOIT désigner le répertoire de tests, désactiver le greffon de test enregistré par la bibliothèque d'accès Ethereum figée, dont le chargement échoue avec les versions récentes de ses propres dépendances, déclarer le marqueur `slow` des tests longs et les exclure de l'exécution par défaut (FR-INT-35).
- **FR-INT-23** : L'environnement d'installation et d'exécution DOIT fournir un outillage de construction Python (setuptools) de version antérieure à 81 : la bibliothèque d'accès Ethereum figée importe, dès son chargement, une interface de gestion des ressources de paquets retirée à partir de cette version. Cette contrainte n'est pas déclarée par le paquet ; sans elle, le mode adresse et l'outil de régénération échouent, tandis que la décompilation d'un bytecode, la génération, la validation et la vérification, qui ne chargent pas cette bibliothèque, restent possibles.

*Note contextuelle : le dépôt contient encore un manifeste d'inclusion de données hérité de l'ancien outillage de construction ; il est sans effet avec le moteur actuel, qui inclut déjà les données. Il contient aussi une configuration du vérificateur de style (quatre règles ignorées, longueur de ligne maximale de 100 caractères) utilisée par l'intégration continue en mode informatif.*

## 5. Intégration continue et versionnage

- **FR-INT-24** : Le workflow de tests DOIT se déclencher à chaque envoi de commits et à chaque demande de fusion visant la branche de travail du dépôt ou la branche `master`, à l'exception des envois et des demandes de fusion dont le commit de tête contient le marqueur `[skip ci]` (ou l'un des marqueurs équivalents reconnus par la plateforme d'intégration continue), cas du commit de version de FR-INT-30.
- **FR-INT-25** : Le workflow de tests DOIT s'exécuter sur une machine Ubuntu, pour chacune des versions Python 3.9, 3.10 et 3.11, l'échec d'une version n'interrompant pas les autres.
- **FR-INT-26** : Le workflow de tests DOIT, dans cet ordre : mettre à jour l'installateur de paquets, installer un outillage de construction antérieur à la version 81, installer le système en mode éditable avec son option `verify`, installer pytest, le vérificateur de style et le sélecteur de versions du compilateur, installer les compilateurs Solidity 0.8.19, 0.8.31, 0.7.6, 0.6.12, 0.5.17 et 0.4.26 (0.8.19 étant activé), construire la base de signatures (un échec de construction fait échouer l'étape), exécuter la suite de tests par défaut en mode verbeux, puis les tests longs (`slow`) en mode verbeux, et enfin le vérificateur de style.
- **FR-INT-27** : Le workflow de tests DOIT exécuter le vérificateur de style sur le code du système en mode informatif uniquement : ses constats sont affichés mais NE DOIVENT jamais faire échouer le workflow.
- **FR-INT-28** : Le workflow de versionnage DOIT se déclencher à chaque envoi de commits sur la branche de travail, à l'exception des envois dont le commit de tête contient le marqueur `[skip ci]` : c'est ce marqueur, porté par le commit de version de FR-INT-30, qui empêche le workflow de se relancer sur son propre envoi.
- **FR-INT-29** : Le workflow de versionnage DOIT lire la version déclarée dans le manifeste du projet et la plus récente étiquette de la forme `vX.Y.Z` (tri par version), partir de la plus grande des deux, en incrémenter le numéro de correctif, et remplacer uniquement la ligne de version du manifeste, sans reformater le reste du fichier.
- **FR-INT-30** : Le workflow de versionnage DOIT ensuite créer, si le manifeste a changé, un commit de message `chore: bump version [skip ci]` dont l'auteur déclaré est le robot d'automatisation (`github-actions[bot]`), envoyer la branche de travail, puis créer et envoyer l'étiquette `v<nouvelle version>` lue dans le manifeste.
- **FR-INT-31** : Le workflow de versionnage DOIT utiliser un jeton d'accès dédié, fourni comme secret du dépôt (`BUMP_VERSION_TOKEN`), pour récupérer l'historique complet et envoyer commit et étiquette.

*Note contextuelle : le workflow de versionnage exclut aussi l'acteur `github-actions[bot]`, mais cette exclusion est inopérante. L'envoi étant authentifié par le jeton dédié de FR-INT-31, l'acteur de l'envoi est le titulaire de ce jeton, et non le robot, dont l'identité ne sert que d'auteur déclaré du commit ; seul le marqueur `[skip ci]` évite la boucle. Ce marqueur a un effet de bord : tant que le commit de version reste en tête de la branche de travail, une demande de fusion issue de cette branche ne déclenche pas non plus le workflow de tests. L'envoi de l'étiquette ne déclenche aucun des deux workflows, qui ne réagissent qu'aux branches.*

*Note contextuelle : la branche par défaut du dépôt distant (`master`) porte l'historique de l'outil amont, alors que le travail propre au système, les deux workflows et les étiquettes de version se trouvent sur une branche de travail distincte. La branche `master` ne contenant pas elle-même ces workflows, un envoi direct sur elle ne déclenche en l'état aucun test ; seuls les envois sur la branche de travail et les demandes de fusion qui incluent les workflows les déclenchent.*

## 6. Suite de tests comme contrat de non-régression

- **FR-INT-32** : Le système DOIT être accompagné d'une suite de tests pytest (2 034 tests collectés à ce jour, dont 1 734 dans l'exécution par défaut, chiffres vivants) couvrant : le pipeline complet sur des bytecodes de référence (fonctions par sélecteur, stockage et sélecteurs résolus, slot de proxy et appel délégué reconstruits, boucles structurées et exécutées sur entrées concrètes) ; l'analyse du dispatch, les métadonnées du compilateur, la mémoire initiale, la sémantique des opcodes et l'exécution symbolique ; la simplification (règles, fuzzing, limite de temps) et le déterminisme des sorties quelle que soit la graine de hachage ; la reconstruction du stockage, des paramètres et des caractéristiques des fonctions ; la détection des slots de proxy ; la base de signatures ; l'entrée invalide et le payload combiné ; le générateur Solidity (interface, commande, relèvement, rendu, passes de réécriture, stockage, recherche du niveau de réécriture vérifié), avec compilation réelle et exécution différentielle contre les références ; la validation par compilation ; le vérificateur (interface, ABI, comparaison de bytecode, disposition du stockage, machines EVM, fuzzing et entrées guidées, contrats simulés, oracle, localisation des compilateurs) ; la reconstruction des références elles-mêmes.
- **FR-INT-33** : Les tests qui compilent DOIVENT trouver le compilateur par la recherche de FR-INT-08, être ignorés automatiquement lorsque la version exacte qu'ils demandent n'est pas installée, et échouer, avec les messages du compilateur, lorsqu'il refuse le code ; les tests qui exécutent du bytecode DOIVENT être ignorés lorsqu'aucune machine EVM n'est disponible.
- **FR-INT-34** : Les bytecodes de référence DOIVENT être des bytecodes runtime stockés chacun sur une seule ligne hexadécimale sans préfixe `0x` ni saut de ligne final (48 à ce jour), produits à partir de leurs sources Solidity (30 à ce jour) par un script de construction selon un registre qui fixe, pour chaque référence, le fichier source, le contrat, la version exacte du compilateur, l'optimiseur et son nombre d'exécutions, le pipeline IR et la version d'EVM ; le script DOIT reproduire chaque bytecode à l'octet près (métadonnées comprises) ou, en mode contrôle, signaler toute différence par un code de sortie non nul, et la suite DOIT vérifier que chaque bytecode est enregistré et se reconstruit à l'identique lorsque son compilateur est installé.
- **FR-INT-35** : Les tests longs DOIVENT porter le marqueur `slow` et être exclus de l'exécution par défaut ; ils s'exécutent avec l'option `-m slow`, nécessaire aussi pour en sélectionner un par son identifiant.
- **FR-INT-36** : La suite DOIT marquer « échec attendu strict » les limites connues qu'elle documente, de sorte qu'un succès inattendu fasse échouer la suite et impose la mise à jour de la documentation de la limite ; c'est aujourd'hui le cas de la disposition du stockage d'une référence dont la source déclare un type que le bytecode ne permet pas d'observer (une adresse lue comme un mot entier).
- **FR-INT-37** : Les exemples exécutables intégrés au composant de filtrage par motifs PEUVENT être exécutés séparément comme tests de documentation ; ils ne font pas partie de la suite.

## 7. Scripts de vérification hérités

- **FR-INT-38** : Le dépôt contient un pipeline d'intégration Jenkins et un script shell local hérités, qui décompilent un contrat déployé fixe récupéré auprès d'un point d'accès RPC public codé en dur, retirent les couleurs de la sortie, vérifient seulement qu'elle n'est pas vide et l'enregistrent sous une extension de fichier Vyper (le pipeline l'archivant en outre comme artefact) ; ces scripts NE DOIVENT PAS être considérés comme faisant partie du contrat d'intégration du système, qui ne dépend d'eux en rien.

*Note contextuelle : ces scripts ne sont plus maintenus et ont été remplacés par les tests sur bytecodes de référence (section 6). Ils sont trompeurs à plusieurs titres : la sortie enregistrée est du pseudo-code et non du Vyper ; l'étape Jenkins intitulée « vérification Vyper » n'invoque aucun compilateur Vyper, et les outils de test installés par le pipeline ne sont jamais exécutés ; le script local tente une compilation Vyper sans jamais échouer et suppose un chemin de dépôt personnel.*
