# Reconstruction Solidity (solgen) et validation par compilation

Ce document (préfixe `SOL`) spécifie le générateur de reconstruction Solidity « best-effort » : ce qu'il lit, la structure du contrat qu'il produit, la traduction des définitions de stockage en variables d'état, la traduction de chaque forme de nœud en instruction ou en expression Solidity, la table des événements connus, les marqueurs d'approximation et de non-résolution, le calcul de confiance, le traitement des fonctions en échec, puis la validation facultative du résultat par un compilateur externe. Le texte exact des lignes produites est fixé ici ; [sorties.md](sorties.md) se contente d'y renvoyer pour les formats `--solidity` et `--combined-json`.

Le vocabulaire des nœuds traduits est défini dans [pipeline-decompilation.md](pipeline-decompilation.md), section 11, et les définitions de stockage dans [reconstruction-fonctions-stockage.md](reconstruction-fonctions-stockage.md), section 4 ; l'accès à ces capacités par la commande et par l'interface Python est décrit dans [architecture.md](architecture.md), sections 7 et 8 ; ce que le système attend du compilateur externe est dans [integration.md](integration.md), section 2. Voir [README.md](../README.md) pour la table des matières du répertoire `docs/`.

Chaque exigence est identifiée par un code FR-SOL-NN. Sauf mention contraire (« DEVRAIT », « PEUT », « NE DOIT PAS »), une exigence est obligatoire (« DOIT »).

## 1. Vue d'ensemble et entrée

Le générateur n'est pas un recompilateur : il transcrit l'AST de décompilation en un contrat Solidity qui compile, en signalant explicitement chaque construction qu'il ne sait pas reconstruire avec certitude, plutôt que de la deviner.

- **FR-SOL-01** : Le générateur DOIT prendre pour seule entrée l'AST JSON d'un résultat de décompilation (listes `functions`, `stor_defs` et objet `problems`), sans ré-exécuter aucune étape de décompilation ; un AST nul ou vide DOIT être traité comme l'objet vide `{}`.
- **FR-SOL-02** : Pour un AST vide, le générateur DOIT produire un contrat réduit à l'en-tête, à la déclaration de l'événement de repli et à l'accolade fermante, avec un dictionnaire de confiance vide et une liste d'avertissements vide, sans signaler que l'AST était vide.
- **FR-SOL-03** : Le générateur NE DOIT ni échouer sur une construction inconnue ni l'omettre silencieusement : toute construction non traduite DOIT être remplacée par un marqueur explicite (sections 3 et 4).

*Note contextuelle : cette garantie n'est pas tenue pour les masques dont la taille ou le décalage n'est pas une constante entière (FR-SOL-35) ; un tel masque, produit par exemple par un décalage `shr` d'une quantité lue dans les données d'appel, provoque une erreur de type qui interrompt toute la génération. L'erreur est propagée à l'appelant et la commande se termine alors avec le code 1, sans aucune sortie Solidity (comportement reproduit sur un bytecode minimal de quinze octets).*
- **FR-SOL-04** : Le générateur NE DOIT PAS prétendre à la fidélité sémantique : types, noms de variables locales, structure du flot de contrôle et paramètres d'événements sont reconstruits par heuristique, et le code produit peut se comporter différemment du bytecode d'origine.

## 2. Structure du contrat produit

- **FR-SOL-05** : Le code produit DOIT commencer par les sept lignes suivantes, suivies d'une ligne vide :

```
// GENERATED BY SCOBELIX SOLGEN
// Best-effort reconstruction of decompiled EVM bytecode.
// This is an approximation, NOT verified/compiled original
// source - see inline `// approximation:` comments for every
// construct that could not be reconstructed with confidence.
// SPDX-License-Identifier: UNKNOWN
pragma solidity ^0.8.0;
```

- **FR-SOL-06** : Le générateur DOIT déclarer un contrat unique nommé `DecompiledContract`, dont le premier membre est la déclaration de l'événement de repli, suivie de son commentaire :

```
event ScobelixUnresolvedEvent(string detail); // approximation: real event ABI not reconstructed
```

- **FR-SOL-07** : Le générateur DOIT déclarer ensuite, triés par nom, les seuls événements connus effectivement émis dans le contrat (section 3.2), sous la forme `event <Nom>(<type> [indexed] <nom>, …);`.
- **FR-SOL-08** : Le générateur DOIT déclarer une variable d'état par emplacement de stockage présent dans les définitions de stockage, la dernière définition d'un emplacement l'emportant lorsqu'il en a plusieurs, dans l'ordre lexicographique de la représentation textuelle des emplacements, avec la visibilité `internal` et les types suivants : pour un mapping, des mappings imbriqués à clés et valeur `uint256` dont la profondeur est la profondeur d'imbrication maximale observée dans les traces pour cet emplacement (au moins 1) ; pour un tableau, `uint256[]` ; pour tout autre type, `uint256`, précédé du commentaire `// storage slot <emplacement>`. La liste des variables d'état est suivie d'une ligne vide lorsqu'elle n'est pas vide.
- **FR-SOL-09** : Le générateur DOIT assainir tout identifiant issu de l'AST en remplaçant chaque caractère autre qu'une lettre ASCII, un chiffre ou `_` par `_`, et en préfixant `v_` un identifiant vide ou commençant par un chiffre.
- **FR-SOL-10** : Le générateur DOIT déclarer, après les variables d'état, une variable synthétique `uint256 internal stor_extra_<N>;` pour chaque emplacement ou référence non résolu rencontré pendant la traduction (sections 3 et 4), N étant attribué à partir de 0 dans l'ordre de première rencontre.
- **FR-SOL-11** : Le générateur DOIT ensuite émettre les fonctions, puis les commentaires des fonctions en échec (section 4), puis l'accolade fermante du contrat suivie d'un saut de ligne final.
- **FR-SOL-12** : Chaque fonction DOIT être précédée d'une ligne vide et d'un commentaire de provenance portant son nom, et avoir pour en-tête, pour l'identifiant `_fallback`, une fonction de repli payable qui reçoit et retourne des octets ; pour tout autre identifiant, une fonction externe sans paramètre, payable si la fonction décompilée l'est, qui retourne des octets, et dont le nom est le nom ABI (à défaut le nom, à défaut l'identifiant) tronqué avant sa première parenthèse (`unnamed` s'il ne reste rien), assaini, et suffixé `_2`, `_3`… en cas de doublon :

```
// reconstructed from function `_fallback(?)`
fallback(bytes calldata) external payable returns (bytes memory) {

// reconstructed from function `<nom>`
function <nom_abi>() external [payable] returns (bytes memory) {
```

- **FR-SOL-13** : Le générateur DOIT déclarer, en tête de chaque fonction et par décalage croissant, une variable locale par paramètre décodé, toujours de type `uint256` quel que soit le type inféré, initialisée par la tranche de 32 octets des données d'appel à ce décalage : `uint256 <nom> = uint256(bytes32(msg.data[<d>:<d + 32>]));`.
- **FR-SOL-14** : Le générateur DOIT déclarer une seule fois, en tête de chaque fonction et par identifiant croissant, une variable locale `uint256 loopvar_<N>;` pour chaque identifiant entier de variable de boucle apparaissant dans la trace de la fonction, afin que toute référence ultérieure, dans n'importe quelle branche, soit valide.

## 3. Traduction des instructions et des expressions

### 3.1 Instructions

Les instructions du corps d'une fonction sont indentées de huit espaces, puis de quatre espaces supplémentaires par niveau d'imbrication.

- **FR-SOL-15** : Un nœud `if` DOIT être traduit en `if (<condition>) {` … `}`, complété d'un bloc `} else {` … `}` lorsque la branche fausse n'est pas vide.
- **FR-SOL-16** : Un nœud `while` DOIT être traduit par l'affectation des valeurs initiales de ses variables de boucle (`loopvar_<N> = <valeur>;`) suivie de `while (<condition>) {` … `}` ; un nœud `continue` DOIT être traduit par les réaffectations qu'il porte suivies de `continue;`.
- **FR-SOL-17** : Un nœud `return` DOIT être traduit en `return <valeur>;`, la valeur étant la variable d'octets de retour de l'appel le plus récent lorsque la valeur retournée désigne des données de retour d'appel, et l'encodage `abi.encode(<expression>)` dans tous les autres cas.
- **FR-SOL-18** : Un nœud `revert` DOIT être traduit, selon ses données et dans cet ordre de priorité, par l'une des formes suivantes : sans données, un rejet sans message ; données contenant une chaîne littérale masquée, un rejet portant ce message (barres obliques inverses et guillemets doubles échappés) ; données se terminant par la valeur 17, un rejet sans message commenté comme dépassement arithmétique ; dans tous les autres cas, un rejet sans message commenté comme approximation :

```
revert();
revert("<message>");
revert(); // panic(0x11): arithmetic overflow/underflow
revert(); // approximation: original revert reason not decoded
```

- **FR-SOL-19** : Un nœud `invalid` DOIT être traduit en `assert(false); // approximation: INVALID opcode`, et un nœud `stop` en `return "";`.
- **FR-SOL-20** : Une écriture de stockage (`store`, ou `set` dans une trace préparée pour l'affichage) DOIT être traduite en affectation `<cible> = <valeur>;` de la variable d'état résolue (section 3.4), la valeur étant toujours convertie en `uint256`.
- **FR-SOL-21** : Un nœud `label` DOIT être traduit en commentaire `// label <identifiant> (no-op)`, et une affectation isolée de variable (`setvar`) en `loopvar_<identifiant> = <valeur>;`.
- **FR-SOL-22** : Un nœud `selfdestruct` DOIT être traduit par le commentaire `// approximation: selfdestruct target not reliably decoded` suivi de `selfdestruct(payable(address(uint160(<bénéficiaire>))));`.
- **FR-SOL-23** : Toute autre instruction (notamment `staticcall`, `create`, `create2`, `precompiled`, `setmem`, `tstore`, `require`, `undefined` et les lignes de commentaire du mode `--verbose`) DOIT être traduite par un commentaire `// unresolved: <représentation>` suivi de `revert("scobelix: unsupported construct");`, comptée comme non résolue et signalée par l'avertissement `unresolved statement opcode: '<opérateur>'`.
- **FR-SOL-24** : Toute représentation textuelle d'un nœud insérée dans un commentaire ou un message DOIT être tronquée à 80 caractères (les trois derniers remplacés par `...`) et ses retours à la ligne remplacés par des espaces.

*Note contextuelle : les instructions de FR-SOL-23 sont fréquentes dans les traces réelles (écritures mémoire résiduelles, appels en lecture seule, gardes issues de la structuration des boucles) ; le contrat généré rejette alors l'exécution à un endroit où le bytecode d'origine poursuivait. C'est l'un des principaux écarts de comportement assumés du générateur.*

### 3.2 Événements

- **FR-SOL-25** : Le générateur DOIT reconnaître un journal d'événement lorsque son premier sujet est une constante égale au haché keccak-256 de la signature de l'un des événements du tableau ci-dessous, que le nombre de paramètres indexés est égal au nombre de sujets restants et que l'événement a au plus un paramètre non indexé ; il DOIT alors émettre `emit <Nom>(<arguments>);`, les arguments étant pris dans l'ordre de déclaration, les paramètres indexés dans l'ordre des sujets et le paramètre non indexé égal aux données du journal.

  | Événement | Types (indexé = I) |
  |---|---|
  | `Transfer` | address I, address I, uint256 |
  | `Approval` | address I, address I, uint256 |
  | `ApprovalForAll` | address I, address I, bool |
  | `OwnershipTransferred` | address I, address I |
  | `Upgraded` | address I |
  | `AdminChanged` | address, address |
  | `BeaconUpgraded` | address I |
  | `Paused` | address |
  | `Unpaused` | address |
  | `Deposit` | address I, uint256 |
  | `Withdrawal` | address I, uint256 |

- **FR-SOL-26** : Chaque argument d'un événement reconnu DOIT être converti selon le type déclaré : `address(uint160(<valeur>))` pour une adresse, `(<valeur> != 0)` pour un booléen, la valeur convertie en `uint256` sinon.
- **FR-SOL-27** : Un journal non reconnu DOIT être traduit par le commentaire `// approximation: event name/parameter types not reliably reconstructed` suivi de `emit ScobelixUnresolvedEvent("<représentation du nœud>");`, et signalé par l'avertissement `log/event reconstruction is approximate (no ABI match)`.

*Note contextuelle : `AdminChanged` ayant deux paramètres non indexés, il ne satisfait jamais la condition de FR-SOL-25 et retombe toujours sur l'événement de repli, bien qu'il figure dans la table.*

### 3.3 Appels externes

- **FR-SOL-28** : Un nœud `call`, `callcode` ou `delegatecall` DOIT être traduit par le commentaire `// approximation: <opérateur> arguments (gas/value/memory slice) are not reconstructed exactly - forwarding the full calldata` suivi de `(bool <opérateur>_ok_<n>, bytes memory <opérateur>_ret_<n>) = address(uint160(<cible>)).<méthode>(msg.data);`, où la méthode est `delegatecall` pour un `delegatecall` et `call` sinon, et où n numérote les appels de chaque opérateur à partir de 1 sur l'ensemble du contrat.
- **FR-SOL-29** : Le générateur DOIT associer toute référence ultérieure à une variable de succès d'appel (variable nommée se terminant par `.success`, telle que `delegatecall_<N>.success`) ou à des données de retour d'appel aux variables du dernier appel émis, et non à l'identifiant d'appel porté par la trace, qui provient d'un compteur partagé avec d'autres opérations.

*Note contextuelle : le résultat d'un `call` ordinaire est l'atome `ext_call.success` (voir [pipeline-decompilation.md](pipeline-decompilation.md), section 6), qui n'est pas une variable nommée : il relève donc de la règle des atomes non traduits (FR-SOL-39) et devient `0 /* unresolved atom: 'ext_call.success' */`. Une garde « rejeter si l'appel a échoué » est alors traduite par une condition toujours vraie, et le contrat généré rejette systématiquement l'exécution après un tel appel, sans que le niveau de confiance soit abaissé (comportement reproduit sur un bytecode minimal).*

### 3.4 Expressions

- **FR-SOL-30** : Un entier positif ou nul DOIT être traduit par son littéral décimal ; un entier négatif n DOIT être traduit par le littéral de 2^256 + n suivi du commentaire `/* n */`, afin de rester compatible avec l'arithmétique `uint256` vérifiée.
- **FR-SOL-31** : Les opérateurs binaires DOIVENT être traduits entre parenthèses, les deux opérandes étant convertis en `uint256`, selon la correspondance : `add` `+`, `mul` `*`, `div` et `sdiv` `/`, `mod` et `smod` `%`, `and` `&`, `or` `|`, `xor` `^`, `eq` `==`, `ne` `!=`, `lt` et `slt` `<`, `gt` et `sgt` `>`, `le` et `sle` `<=`, `ge` et `sge` `>=` ; une addition à plus de deux termes DOIT être traduite en somme parenthésée de tous ses termes.

*Note contextuelle : les opérateurs signés sont traduits par leurs équivalents non signés sans commentaire d'approximation.*

- **FR-SOL-32** : Un test de nullité DOIT être traduit en `(!<ok>)` lorsqu'il porte sur une variable de succès d'appel (FR-SOL-29), en `(!<expression>)` lorsqu'il porte sur une expression booléenne (comparaison ou autre test de nullité), et en `(<expression> == 0)` sinon ; `not` DOIT être traduit en `(~<expression>)`.
- **FR-SOL-33** : Une référence à un paramètre nommé DOIT être traduite par le nom assaini du paramètre, une variable de boucle par `loopvar_<N>`, et toute autre variable nommée par une variable d'état synthétique (FR-SOL-10), avec l'avertissement `unresolved named var: '<nom>'`.
- **FR-SOL-34** : Une lecture ou un emplacement de stockage DOIT être résolu ainsi : un emplacement simple par le nom de la variable d'état déclarée pour ce numéro (à défaut, par une variable synthétique) ; un accès de mapping par `<base>[<clé>]`, récursivement pour les mappings imbriqués, la clé étant convertie en `uint256` ; toute autre forme d'emplacement (tableau, longueur, emplacement nommé d'après un getter, emplacement symbolique) par une variable synthétique, comptée comme non résolue et signalée par l'avertissement `unresolved storage index shape: <représentation>`.
- **FR-SOL-35** : Un masque `mask_shl` dont la taille et le décalage sont des constantes entières DOIT être traduit ainsi : l'extraction du sélecteur des données d'appel (256 bits, décalages ±224, lecture du mot 0) par `uint32(bytes4(msg.sig))` ; un masque de 160 bits par `address(uint160(<valeur>))` ; un masque de décalage positif ou nul par la valeur combinée par un « et » bit à bit (`&`) avec le masque entier correspondant (omis pour 256 bits au décalage 0), puis décalée à gauche ou à droite selon le signe du décalage de sortie ; un masque de décalage négatif par la valeur précédée du commentaire `/* approximation: mask_shl(<taille>,<décalage>,<sortie>) */`, avec l'avertissement `mask_shl(<taille>,<décalage>,<sortie>) not exactly reconstructed`.
- **FR-SOL-36** : Les décalages `shl`, `shr` et `sar` DOIVENT être traduits en `(<valeur> << <n>)` ou `(<valeur> >> <n>)`, `sar` étant approximé par un décalage logique avec l'avertissement `sar approximated as logical (unsigned) shift`.
- **FR-SOL-37** : Un haché `sha3` DOIT être traduit par le haché d'une tranche vide des données d'appel suivi d'un commentaire `/* approximation: … */` décrivant la zone hachée, avec l'avertissement `sha3 region reconstruction is approximate`.
- **FR-SOL-38** : Une lecture d'un mot des données d'appel DOIT être traduite en `uint256(bytes32(msg.data[<d>:<d> + 32]))`, une tranche des données d'appel en `msg.data[<début>:<début> + <longueur>]`, une suite de données brute en `hex"" /* approximation: raw data blob */`, et un booléen littéral en `true` ou `false`.
- **FR-SOL-39** : Les atomes DOIVENT être traduits comme suit : taille des données d'appel en `msg.data.length`, `caller` en `msg.sender`, `address` en `address(this)`, `gas` en « gasleft() », les données de retour d'appel en variable de retour du dernier appel, une chaîne littérale entre apostrophes en chaîne Solidity entre guillemets doubles (échappée) ; tout autre atome DOIT être traduit en `0 /* unresolved atom: <représentation> */`.

*Note contextuelle : les atomes `origin`, `timestamp`, `number` et `callvalue` relèvent de cette dernière règle et sont donc traduits par un zéro commenté ; des traductions vers `tx.origin`, `block.timestamp` et `block.number` sont prévues par le générateur, mais dans une branche que les atomes n'atteignent jamais.*

- **FR-SOL-40** : Lorsque le contexte impose une valeur `uint256` (opérandes, clés de mapping, écritures de stockage, arguments d'événements), le générateur DOIT convertir une adresse masquée en `uint256(uint160(…))`, un booléen littéral en `1` ou `0`, `caller` en `uint256(uint160(msg.sender))` et `address` en `uint256(uint160(address(this)))`.
- **FR-SOL-41** : Toute autre expression DOIT être traduite en `0 /* unresolved: <représentation> */`, comptée comme non résolue et signalée par l'avertissement `unresolved expression opcode: '<opérateur>'` ; une valeur qui n'est ni un entier, ni une chaîne, ni un nœud (par exemple un nombre à virgule) DOIT être traduite en `0 /* unresolved atom: … */` et comptée comme non résolue.
- **FR-SOL-42** : Toute construction approximée DOIT porter un commentaire contenant `approximation:` et toute construction non résolue un commentaire contenant `unresolved:` ou `unresolved atom:`, de sorte qu'aucune supposition ne soit silencieuse.

## 4. Confiance, avertissements et fonctions en échec

- **FR-SOL-43** : Le générateur DOIT calculer pour chaque fonction un niveau de confiance à partir du rapport entre le nombre de nœuds comptés comme non résolus et le nombre total de nœuds traduits (instructions et expressions) : `high` si ce rapport est nul, `medium` s'il est strictement inférieur à 0,1, `low` sinon, et `medium` si aucun nœud n'a été traduit ; ce niveau est associé à l'identifiant de la fonction (`?` à défaut).
- **FR-SOL-44** : Le générateur DOIT retourner la liste de tous les avertissements émis pendant la génération, dans leur ordre d'émission, doublons compris.

*Note contextuelle : seules les instructions non traduites, les formes d'emplacement non résolues, les expressions non traduites et les valeurs non textuelles abaissent la confiance ; les approximations (masques à décalage négatif, `sar`, `sha3`, variables nommées, événements de repli) et les atomes non traduits sont signalés par des commentaires ou des avertissements sans modifier le niveau de confiance.*

- **FR-SOL-45** : Pour chaque fonction de la liste des échecs de décompilation, le générateur DOIT émettre, après les fonctions, une ligne vide puis les deux commentaires `// decompilation failed for selector <identifiant> (<nom>)` et `// @custom:scobelix-confidence none`, de sorte que l'échec reste visible dans le contrat ; ces fonctions n'ont pas d'entrée dans le dictionnaire de confiance.

*Note contextuelle : la documentation d'usage annonce pour ces fonctions un « stub explicite qui rejette l'exécution » ; le générateur actuel n'émet en réalité que ces deux commentaires, sans fonction ni instruction de rejet.*

## 5. Validation par compilation

- **FR-SOL-46** : La validation DOIT utiliser le compilateur désigné par un chemin explicite ou, à défaut, le premier binaire `solc` trouvé dans le `PATH` ; en l'absence de compilateur, elle DOIT retourner le statut `skipped`, aucune erreur et l'avertissement `solc not found on PATH - validation skipped`, sans lever d'exception.
- **FR-SOL-47** : La validation DOIT écrire le code source dans un fichier `Decompiled.sol` d'un répertoire temporaire créé pour l'occasion (cycle de vie dans [integration.md](integration.md), section 3), puis invoquer le compilateur avec l'option `--bin` sur ce fichier, en capturant ses sorties sous forme de texte, dans la limite d'un délai maximal (30 secondes par défaut).
- **FR-SOL-48** : Un dépassement du délai DOIT produire le statut `skipped` avec l'avertissement `solc timed out after <délai>s`, et un échec du lancement du compilateur (binaire introuvable ou non exécutable au chemin fourni) le statut `skipped` avec l'avertissement `solc invocation failed: <erreur>`.
- **FR-SOL-49** : Les erreurs DOIVENT être les lignes de la sortie d'erreur du compilateur qui commencent, une fois débarrassées de leurs blancs initiaux, par `Error`, et les avertissements celles qui commencent par `Warning`.
- **FR-SOL-50** : La validation DOIT retourner le statut `invalid` lorsque le compilateur termine avec un code non nul ou qu'au moins une ligne d'erreur est présente, la liste des erreurs contenant alors les lignes d'erreur ou, à défaut, l'intégralité de la sortie d'erreur ; elle DOIT retourner le statut `valid`, sans erreur, dans le cas contraire ; les avertissements sont retournés dans les deux cas.
- **FR-SOL-51** : Le statut `valid` DOIT être interprété comme la seule attestation que le code généré compile ; il ne garantit en rien la fidélité de ce code au bytecode d'origine.
